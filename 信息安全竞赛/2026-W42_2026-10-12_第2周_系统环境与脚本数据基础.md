## 一、安全工作区与命令模型

### 本章路线

先分清“谁解释命令、命令处理谁” → 用路径定位材料 → 用文件类型和摘要保存原件 → 理解文件与目录权限 → 在可控目录完成附件分析。

> 本章要解决的问题：拿到题目附件后，怎样找到并读取正确对象，而不因为路径、覆盖或权限操作把材料弄坏？
>
> 本章学完应会：解释命令和参数；从当前目录推导相对路径；识别只读观察、结果写入与权限变化；为每一步保留可核对证据。

### 学习单元

#### 1. Shell、命令和参数：把动作交给哪个程序

**Shell** 是读取并解释命令的程序，终端窗口是和它交互的界面。Bash与PowerShell都属于Shell，但语法不同：本章标为 `bash` 的代码应在Bash执行，不能把管道中的程序名直接照搬到PowerShell。打开窗口不代表安装了Linux，也不代表当前Shell就是Bash。

一条命令通常包括程序名、选项和操作对象。选项调整动作，参数提供对象。例如：

```bash
head -n 3 '第2周_access.log'
```

`head` 是程序，`-n 3` 指示读前三行，最后一个参数是文件名。单引号告诉Bash按字面把内容作为一个参数；名称里有空格时尤其重要。它读取文件，将内容写到屏幕，不改变文件。

思考命令时先用自然语言复述：“对哪个文件做哪种只读处理，结果去哪？”若说不清动作，不应仅因答案里出现这条命令就执行。

#### 2. 当前目录与路径：从起点走到材料

**当前工作目录**是相对路径的起点；**绝对路径**从根目录开始。假设下列目录是教学模型，不要求你机器上真的存在：

```text
case/
  input/events.log
  out/
```

当前目录为 `case/` 时，`input/events.log` 指向输入；当前目录为 `case/out/` 时，相同字符串会尝试找 `case/out/input/events.log`，通常不存在。此时 `../input/events.log` 才指向原来的输入。`.` 表示当前目录，`..` 表示父目录，不是授权范围的标志。

```bash
pwd
ls -l
head -n 2 'input/events.log'
```

先用 `pwd` 看到起点，再用 `ls -l` 查看名称、类型和权限，最后读取已确认对象。`cd` 改变起点，例如 `cd out` 后再执行相对路径命令，目标可能变化。**同一个路径字符串不一定是同一个文件**，这解释了不少“脚本昨天能读，今天找不到”的问题。

边界：符号链接可以把目录内名称指向目录外。仅检查字符串以 `case/` 开头，不足以确认真正目标在工作区内；第六章会用解析后的路径检查静态范围。不要对尚未确认的路径递归删除或移动。

#### 3. 普通文件、目录、符号链接和后缀

普通文件保存数据，目录组织名称，符号链接保存到另一个路径的指向。`ls -l` 一行的首字符常以 `-` 表示普通文件、`d` 表示目录、`l` 表示符号链接。

文件后缀只是名称约定，不是内容证明。`photo.jpg` 可能根本不是图片；竞赛附件分析先看内容签名或文件识别结果，再决定解析器，而不是“改后缀就修好了”。

```bash
file 'photo.jpg'
head -n 2 'events.log'
```

假如 `file` 报出 `PNG image data`，当前能下的结论是“该工具按内容识别为PNG”，不是“文件没有隐藏数据”。识别类型只是选择后续方法的第一步；不要把未知二进制直接当程序运行，也不要用文本编辑器保存它来消除乱码。

#### 4. 原始字节、工作副本和摘要：怎样发现材料变了

**摘要（hash）**把任意长度输入映射为固定长度值。本周用SHA-256作完整性对照：相同字节得到相同摘要；改一个换行也可能得到完全不同的值。摘要不是加密，不能由摘要还原文件，也不能仅凭摘要证明来源可信。

```bash
mkdir -p 'work/input' 'work/out'
cp '第2周_access.log' 'work/input/access.log'
sha256sum '第2周_access.log' 'work/input/access.log'
```

`mkdir -p` 创建需要的目录；`cp` 复制；`sha256sum` 每行输出摘要和名称。应看到两个摘要相等，再在副本上分析。若摘要不等，先查复制、编码/BOM或换行转换，不把差异直接当“发现攻击”。不要伪填固定摘要；实际值由原文件计算。

保存输入摘要、程序版本和结果路径，能让队友判断“我们算的是不是同一份材料”。排序后的文件是派生材料，应另存，不能回写原件。

#### 5. 文件权限与目录搜索：能看见不等于能读取

Linux常用权限把主体分成所有者、所属组、其他用户，动作分成读 `r`、写 `w`、执行/搜索 `x`。例如 `-rw-r-----`：普通文件；所有者可读写；组可读；其他无权限。数字模式把读/写/执行分别记为4/2/1，`640`等于三组 `rw- / r-- / ---`，不是“640级安全”。

文件的读允许读取内容；目录的读允许列出名称；目录的搜索 `x` 允许按已知名称访问其中对象。实际读 `case/input/a.log` 通常要求路径上各目录有搜索权限，还要对 `a.log` 有读权限。

具体对照：目录 `--x` 的主体可能知道 `a.log` 名称后能访问它，却不能列出目录；目录 `r--` 的主体可能列出名字，却不能正常沿路径访问对象。访问控制列表、管理员权限、挂载选项等还可能影响结果，这里只是基本权限模型，不把一条错误消息当最终原因。

##### 小练习：权限不是一个总开关

> 题源：依据Linux路径解析与GNU chmod原手册改写的自拟题；不涉及真实账户变更。

已知父路径都可搜索，`input/` 对分析用户权限为 `--x`，`a.log` 为 `r--`。用户知道 `a.log` 名称。比较 `ls input/` 与读取 `input/a.log`；若文件改成 `---`，哪个判断改变？

<details><summary>先尝试，再看解析</summary>

基本模型下：列名称缺目录读权限，失败；读取已知文件具备目录搜索和文件读权限，可成功。文件改成 `---` 后读取也失败，但列目录本来就失败。这不是通过“给目录777”解决题目：先分清需要列名称还是读取已知对象，再判断最少动作。

</details>

#### 6. 最小授权与停止线：安全准备不是刷命令

**最小授权**是只给确实需要的主体和动作，不以“能跑起来”为由放开全部权限。假如读取附件失败，先核对路径、对象类型、用户和错误原文，再在明确授权下修改工作副本的必要权限；不对整个主机 `chmod -R 777`。

安全操作也要区分逻辑错误与环境错误：文件不存在是路径/输入问题，不是“没有事件”；错误输出不是数据。到工作区之外、碰到不明程序或需要更高权限时停下来确认。这里只演示本地已知文本，不扫描或连接任何示例地址。

## 二、路径、权限、进程与环境

### 本章路线

从磁盘上的程序到运行中的进程 → 检查进程的目录和解释器 → 理解环境配置 → 分开结果、诊断和退出码 → 定位“脚本没输出”的真正原因。

> 本章要解决的问题：同一段脚本为什么在队友机器上找不到命令、读不到材料或输出不同？
>
> 本章学完应会：按程序、目录、环境、输入、标准流和退出状态六项定位失败，而不是不停加权限或换命令。

### 学习单元

#### 1. 程序与进程：文件和运行实例不同

**程序**是存储的指令，Python脚本是由解释器执行的代码；**进程**是一次运行实例。两个终端同时启动同一脚本，会产生两个运行实例，输入/目录可能不同。进程还包含运行身份、环境变量和打开的输入输出通道。

例如运行 `python parser.py input.log`，先发生解释器查找，再由解释器读取脚本，最后脚本尝试打开 `input.log`。三层可以分别失败：没有Python、脚本路径不对、数据路径不对。把三种错误都写成“解析器坏了”就失去了定位线索。

Bash内建命令如 `cd` 会改变当前Shell状态；外部命令通常在子进程运行。子进程能继承目录/环境，但它自己的目录变化不能自动让父终端改目录。这解释了为什么脚本里 `cd` 后，你的终端位置可能没变。

#### 2. 工作目录不是脚本所在目录

这是很重要的复现区别。给定：

```text
case/
  tools/parser.py
  input/access.log
```

从 `case/` 执行 `python tools/parser.py input/access.log`，脚本相对读入路径从 `case/` 起算。若从 `case/tools/`执行 `python parser.py input/access.log`，就寻找 `case/tools/input/access.log`。**Python不会因为脚本在tools里就把所有相对路径自动解释成脚本目录**。

最小核对方式是记录 `pwd`、命令行和传入的路径。需要脚本目录作为基准时，要在代码中明确选择该基准；第六章用 `Path` 演示。不要同时隐式使用两种起点。

#### 3. PATH、解释器和版本：命令名如何变成程序

`PATH` 是用于查找命令的目录列表。例如输入 `python` 而不是绝对路径时，Shell会按规则寻找可执行入口。Bash还可能有别名、函数等优先级，查看 `command -v` 和 `type` 比猜更可靠。

```bash
command -v python
python --version
command -v grep
```

如果第一条指向 `env-a/bin/python` 而队友指向 `env-b/bin/python`，同名命令可能使用不同版本/库。`command not found` 说明命令解析失败，不代表输入日志没有内容；`Permission denied` 又是另一类错误。只记录“用了python”不足以复现。

Windows上有时 `python` 是系统应用别名而不是实际解释器。先核对 `python --version` 是否真的返回版本；不可用时停止环境排错，按第六章给出的代码做手算或用已确认的Python环境，不要求安装未知来源软件。

#### 4. 环境变量：影响运行但不在脚本里的配置

环境变量是一组传给进程的名称和值。例如语言环境影响部分文本排序/字符解释，输入目录也可能被程序从环境读取。Bash的 `NAME=value` 赋值只设置Shell变量，`export NAME` 才让后续子进程继承它；`NAME=value command` 可只对一次命令设置环境。

```bash
LC_ALL=C sort 'states.txt'
```

这里把此命令的语言环境设为 `C`，便于稳定按字节序排序简单标识。它不是通用的中文语义排序，也不改变输入文件。应写明比较对象和排序规则，不能把某机器的默认排序当唯一事实。

环境变量还可能包含秘密令牌。只记录与复现有关的非敏感名称/配置，不把完整 `env` 输出贴到公开WriteUp。密码、token和实际用户信息不属于教学样例。

#### 5. 三条标准流：数据和诊断要分开

**标准输入**供程序读数据（编号0），**标准输出**放正常结果（编号1），**标准错误**放诊断（编号2）。编号就是默认通道的标识，不是行号。虽然输出和错误都可能显示在屏幕，它们用途不同。

```bash
grep -nF '403' 'missing.log' > 'hits.txt' 2> 'errors.txt'
```

`-n`显示行号，`-F`把403当固定文字；输入不存在时，错误进入 `errors.txt`，正常结果文件可能已创建但为空。**文件被创建不证明分析成功**。反过来，成功结果写入文件后终端不显示内容，也不能说命令“没运行”。

第三区分会用管道连接数据通道；如果把错误合并进数据，后续统计可能把“文件不存在”作为日志行。这就是三条流在竞赛脚本和日志处理中的直接用途。

#### 6. 退出状态：没有匹配不是读入失败

程序返回一个退出状态给调用者。Bash中的 `$?` 保存**最近一条命令**的退出状态，必须紧接着保存，否则下一条命令会覆盖。

GNU grep常见约定：0为找到匹配，1为无匹配，2为错误；具体工具可有不同约定，不能把所有非零都解释成崩溃。

```bash
grep -nF '403' 'access.log' > 'hits.txt' 2> 'errors.txt'
rc=$?
printf 'grep退出码=%s\n' "$rc"
```

`rc=$?`保存状态，`printf`按格式输出，`%s`放变量的字符串值。若先运行 `echo done` 再取 `$?`，取到的是 `echo` 状态，不能证明grep读入成功。

##### 小练习：空文件加0退出码够不够

> 题源：依据GNU grep Exit Status自拟的错误审查。

某记录：“hits.txt为空，最后 `echo done` 的退出码是0，所以没有403。”给出两个不同反例，以及应增加哪些证据。

<details><summary>解析</summary>

反例1：grep无匹配，原退出码1；反例2：输入不存在，grep原退出码2，但 `echo` 成功后两者都显示0。应在grep后立刻保存状态、查看错误文件、确认输入存在/摘要和过滤范围。无匹配只支持该输入范围内没有满足条件的行，不支持“网站安全”。

</details>

### 竞赛应用示范：队友的日志脚本只生成空结果

**比赛帮助：**它减少把环境故障当作“题目没有线索”的误判。仍不能由一条403确认漏洞或攻击，相关机制和证据要在第四章分析。

## 三、数据流：管道、重定向与文本工具

### 本章路线

先定义一条记录的字段 → 比较文字搜索与字段判断 → 抽取、排序、计数 → 用管道连接步骤 → 看重定向顺序与原件保护。

> 本章要解决的问题：怎样从一批日志里准确统计题目要求的事件，不把路径里的403或损坏行误算进去？
>
> 本章学完应会：对给定格式解释每一步的数据形态，写字段筛选与统计链，检查丢失/异常记录并避免重定向覆盖输入。

### 学习单元

#### 1. 记录、字段、分隔符与格式契约

**记录**是一个事件的数据，**字段**是一条记录中的某个属性。文件的一行是否正好一条记录，需要格式说明确认。本周访问附件的契约是：非空、非 `#`开头的数据行按空白分成**七字段**，依次为时间、方法、路径、状态、用户、来源、会话。`-`表示未提供值，`???`表示未知状态，单独一行 `-`是损坏记录。

```text
2026-10-12T09:15:44+08:00 GET /admin 403 alice 203.0.113.10 s-17
```

状态是第4字段，来源第6，会话第7。不能沿用五字段假设；也不能对包含引号和空格的别的日志照用本契约。

这里引入 **awk**：逐行读文本、将每行分为字段，并在条件满足时执行动作的工具。基本写法是 `awk '条件 {动作}' 文件`；`$0`是整行，`$4`是第4字段，`NF`是本行字段数，`NR`是原始输入行号。未指定分隔规则时，常见awk以空白分字段。

```bash
awk '!/^#/ && NF != 0 && NF != 7 {print NR, $0}' 'access.log'
```

`/^#/`判断开头为#，前面的 `!`取反；`&&`要求条件同时满足；`NF != 0`排除空行；`NF != 7`找到字段异常。动作输出原行号和原文。注释不计事件，坏行保留位置。

#### 2. 固定文字、正则与语义过滤

`grep -F '403'`查找固定字符序列；默认grep模式则可含正则符号。**正则表达式**是描述文字形态的规则，例如 `^`约束行首，`.`表示一个匹配字符（不是字面点）。匹配形式不等于识别业务含义。

看两个输入：

```text
t1 GET /help/403 200 alice ip1 s1
t2 GET /admin 403 alice ip1 s1
```

`grep -F '403'`会命中两行，但题目要状态403时，只能取第二行。正确方法是 `awk 'NF == 7 && $4 == "403" {print}'`；`==`比较字段值，字符串写双引号，省略print参数时打印整行。方法选错，统计再精准也在算错对象。

##### 小练习：请求路径中的401

> 题源：自拟日志语义过滤题。

三行：`t1 GET /docs/401 200 - ip1 -`、`t2 GET /login 401 - ip2 -`、`broken 401`。比较固定串搜索与“合法七字段、状态401”的结果，并写异常行处理。

<details><summary>解析</summary>

文字搜索命中三行；字段统计只保留第二行，第一行状态为200，第三行字段数为2应进异常列表而不是算401。检查步骤是先字段合法性、再状态含义、最后统计，不先grep后假定全是合法事件。

</details>

#### 3. 抽取字段：每一步的输出格式要知道

例如 `awk 'NF == 7 && $4 == "403" {print $6}' access.log` 只输出来源。原先每行七字段，现在每行一个来源；后续程序不再能用 `$4`找状态。

假设筛选后得到：

```text
ip-a
ip-b
ip-a
```

这个输出是“403记录的来源列表”，不是用户列表，也还不是次数表。字段投影丢弃其他信息，若后续需要回到事件时间，应该同时另存原始匹配行或原行号。

`cut -d' ' -f4`按字面空格分隔，多空格可能产生空字段；本周的空白分字段模型用awk更容易表达。真实格式若含引号、嵌入空格或转义，需对应解析器，不能只更换分隔符碰运气。

#### 4. 排序与计数：为什么uniq前通常先sort

`uniq -c`合并**相邻**重复行并显示次数。对 `ip-a, ip-b, ip-a`直接计数是三段各1；先排序变成 `ip-a, ip-a, ip-b`，再计数才能获得ip-a为2、ip-b为1。

```bash
LC_ALL=C sort 'sources.txt' | uniq -c
```

输出次数在前、来源在后。若需要按次数降序，再加 `sort -nr`：`-n`把开头的数字按数值比较，`-r`反向。默认字典排序与数字排序不同，例如文字的 `10`可能排在 `2`之前，次数排序不能遗漏这一点。

注意：按来源计数不等于按攻击者计数；一来源可能共享，来源身份在第四章再核对。

#### 5. 管道：把上一步结果当下步输入

`A | B`把A的标准输出作为B的标准输入，一步不一定生成一个中间文件。完整链可写为：

```bash
awk '!/^#/ && NF == 7 && $4 == "403" {print $6}' 'access.log' |
  LC_ALL=C sort |
  uniq -c |
  sort -nr
```

第一步输出来源列表，第二步聚合同名来源，第三步生成次数表，第四步按次数排序。每一步的形态变化都能用小样例手算。

默认Bash管道退出状态通常是最后一个命令的状态：即使前面读入失败，最后sort仍可能成功。这并不保证完整链成功。第五章讲 `pipefail`和显式错误分支；初学时先将复杂链拆开，核对每步输入行数、异常数与状态。

#### 6. 覆盖、追加和重定向顺序

`>`覆盖输出文件，`>>`追加；`2>`单独存错误。Bash在执行程序前处理重定向，所以 `sort a.log > a.log`可能先清空a.log，再让sort读到空输入。这是原件丢失风险，不是工具随机故障。

顺序也有区别：

```bash
command > result.txt 2>&1
command 2>&1 > result.txt
```

第一条先把标准输出指向文件，再把错误也指向这个输出，因此二者都进文件。第二条先让错误跟随当时的标准输出（通常屏幕），再改变正常输出，错误可能仍去屏幕。`2>&1`复制当前通道指向，不是永久把两条流绑在一起。题目处理结果与诊断最好先分别存，必要时才合并。

### 竞赛应用示范：统计谁对受保护路径收到403

> 题源：第二周合成访问附件；赛题式日志分析，不是实际攻击归因。

**需求：**仅对七字段记录、路径精确为 `/admin`、状态为403，统计每个来源的次数。统计时跳过#注释和空行，字段损坏行另列。

**方法：**不是 `grep admin | grep 403`，因为字符串可能出现在别的字段。先按契约判断，投影来源，再排序计数：

```bash
awk '!/^#/ && NF == 7 && $3 == "/admin" && $4 == "403" {print $6}' '第2周_access.log' |
  LC_ALL=C sort | uniq -c
```

**按附件手算结果：**`198.51.100.7`为1次，`203.0.113.10`为1次；另有第17行（单独 `-`）为字段损坏。`???`行是七字段但状态未知，不能自动算403。

**用途与边界：**题目若要求“提交出现最多的来源”时，还须处理并列、输入完整性和输出格式。此处两者并列，不能任意选一个当唯一答案；来源计数不能证明具体用户、漏洞或恶意动机。

### 本章小结

日志分析先约定记录/字段，再做语义筛选；投影改变数据形态，sort与uniq顺序决定统计含义。管道和重定向节省操作，但不能隐藏错误、覆盖原件或制造“唯一最高”结论。

## 四、日志字段、时间线与证据边界

### 本章路线

先知道各字段在记录什么 → 把时间转到可比较基准 → 分开来源、用户、会话和对象 → 按已知键关联 → 写有证据边界的题目答案。

> 本章要解决的问题：怎样由登录事件和访问记录判断访问过程，而不把同一IP、200或相近时间误当作身份/权限证明？
>
> 本章学完应会：给每个结论附记录出处，区分认证和授权，选择关联依据，指出缺失材料或时间矛盾。

### 学习单元

#### 1. 字段语义：HTTP状态和业务事件不是同一种结果

访问日志记录请求的HTTP处理结果；认证事件记录登录/授权动作的业务结果。HTTP的200表示请求处理成功这一类语义，并不保证页面正文表示“登录成功”。有些应用返回200，但正文写“密码错误”；此时必须再看业务结果。

401通常与缺少有效认证凭据有关，403表示服务端理解请求但拒绝满足；不能普遍断言401必然密码错、403必然已登录。要解释当前题目，还需给定的应用规则。第二周里我们把 `action=login,result=success`视为登录事件成功，把 `action=authorize,result=allow`视为给定对象授权允许；这是**本题的解释契约**，不是所有系统统一格式。

例子：`alice /admin 403`加上alice登录成功，只能提示“身份认证与对象权限可能不同”，不支持“alice得到管理员权限”。字符串 `denied` 在登录事件中表示认证拒绝，在授权事件中表示授权拒绝，先看action再解释result。

#### 2. 时间、时区和顺序：相邻行未必相邻事件

时间戳是事件时刻的一种表示，时区偏移说明该表示相对UTC差多少。本周 `2026-10-12T09:15:44+08:00`表示UTC时刻01:15:44，减去8小时，不是把日期随意改成你电脑的日期。

```text
A：2026-10-12T09:00:00+08:00
B：2026-10-12T01:00:30+00:00
```

转换到UTC后A是01:00:00，B是01:00:30，因此B晚30秒。直接比较原字符串的09和01会反过来。两个带不同偏移的ISO字符串不适合简单字典排序；要解析为时间对象或手算到同一基准。

文件行序也可能因缓冲、汇总或异步写入乱序。原行号用于追溯，不用于代替事件排序。即使时区相同，不同机器时钟也可能漂移；题目未给同步精度时，不把差1秒解释成确定因果。

##### 小练习：时间排序的反例

> 题源：自拟取证时间线题。

上述A、B来自两台机器，时钟最大各误差±20秒。先回答标称时刻谁晚，再说明是否能保证真实事件也按同一顺序发生。

<details><summary>解析</summary>

标称B晚30秒；两台机器相对差可能最多40秒，因此真实顺序仍可能反转。报告应保留“按标称时间B晚30秒；在给定误差范围内因果顺序未定”。排序结果不等于因果证明。

</details>

#### 3. 来源、用户、会话和对象：四个不同问题

**来源**如IP描述网络入口，**用户**是应用绑定的身份，**会话ID**把多次请求连接起来，**对象**是这次操作的资源。IP可能被代理或共享，用户字段可能缺失，会话还可能失效或被复制，任何单字段都不应自动升级为真实个人身份。

```text
记录A：source=ip-shared, user=alice, session=s-a, object=/profile
记录B：source=ip-shared, user=bob, session=s-b, object=/admin
```

可直接观察“来源相同”，也可观察“应用记录了不同用户/会话”；没有证据将两条当作同一人。反过来alice从两个来源使用同会话，也不必然是两个人：可能网络切换，也可能会话复制，需要别的证据。

先固定题目要求是来源统计、用户活动还是会话关联，然后选字段。题目让提交“来源IP”时不要擅自改成用户；要求“主体”而日志只给IP时应说缺证据。

#### 4. 强关联键、时间窗口和矛盾

关联是按规则把不同来源记录配对。题目保证会话ID唯一时，同一ID提供强于同IP的关联；若只按用户加短时间窗口则是候选关联，可能多对多。规则必须写明键、是否允许缺值以及一个请求能匹配几个事件。

第二周已有 `s-17`访问和 `session_id=s-17`认证。可以关联同一给定会话的活动；但原认证记录e-001在09:13:58，POST /login访问在09:14:08，不能仅凭相同ID就断言前者是**后者请求直接产生**。可能记录来源、采集延迟、不同动作或合成材料的简化；当前资料不足以确认原因。

同理09:29:05的GET /logout与09:30:00的logout事件缺少业务规则，不能宣布09:29:05即撤销成功。不要“为了讲顺流程”偷偷改日志：保存矛盾并降低结论范围，才是真正的取证能力。

#### 5. 事实、条件推断与待核实：如何写答案

一条合格结论包含“观察→依据→适用条件→局限”。例如：

- 事实：访问附件第6行有alice、`/admin`、403、s-17。
- 条件推断：若主体绑定和路径规则可信，该会话的这次后台请求被拒绝；先前登录成功不保证后台权限。
- 待核实：拒绝是角色不足、会话过期、访问策略还是其他原因？需要授权规则/业务日志。

报告不是越谨慎越含糊。题目给了足够规则，就应给明确结果；题目缺规则时，指出具体缺什么，而不是一律“可能有问题”。可复核答案不必长，但不能用故事替代字段。

## 五、Shell脚本：从一次命令到可重复流程

### 本章路线

把手动命令封装为有参数的Bash脚本 → 学会引用和分支 → 固定输入范围 → 区分中间/最终输出 → 用反例测试错误行为。

> 本章要解决的问题：换输入、遇到无匹配或读入失败时，怎样不输出一份看似完整的错误报告？
>
> 本章学完应会：跟做一个完整统计脚本，解释参数、变量和分支，给正常/失败/边界样例制定回归判据。

### 学习单元

#### 1. 参数、变量和引用：避免空格拆分

脚本是按顺序执行命令的文本。第一行 `#!/usr/bin/env bash`指示合适环境下用Bash解释；本周更明确地用 `bash count-status.sh ...`启动，不要求更改可执行权限。

Bash中 `$1`是第一个位置参数，`$#`是参数个数，`name=value`赋值不能在等号旁加空格。`"$name"`展开变量且保留一个参数；不加引用可能发生分词或通配符展开。

```bash
input='my logs/access.log'
head -n 2 "$input"
```

此处input包含空格，但双引号让head收到一个文件名，而不是两个参数。单引号保持完全字面，双引号允许变量展开。这是解释参数的规则，不是过滤安全攻击的万能措施；不要使用 `eval`把数据重新当命令执行。

#### 2. 条件、分支与返回值：给错误不同含义

`if 条件命令; then ...; else ...; fi`按条件命令退出状态选择分支。`test`或 `[ ... ]`用于判断，`-f`检查普通文件，`-r`检查可读，`-z`检查空字符串。括号内必须有空格。

```bash
if [ "$#" -ne 1 ]; then
  printf '用法：bash count-status.sh 输入日志\n' >&2
  exit 2
fi
```

`-ne`是整数“不等”，`>&2`把提示输出到标准错误，`exit 2`让调用者收到失败状态。参数数量错与结果零匹配不是一回事。显式分支比裸加 `|| true`诚实：后者可能把不存在、拒绝读取和无匹配都吞成正常。

`set -e`也不是魔法，存在条件、管道等上下文细节；本周对关键步骤显式检查。启用 `set -o pipefail`可使管道不只反映最后一步，但仍需定义哪些非零是可接受的无匹配。

#### 3. 循环、输入白名单与固定对象

循环把同一个操作应用到多个对象。Bash的简单形式是 `for f in ...; do ...; done`。先把对象列清，再循环；不要让生成的 `out/*.txt`成为下一轮输入。

```bash
for f in 'input/a.log' 'input/b.log'; do
  printf '检查文件：%s\n' "$f"
  if [ ! -r "$f" ]; then
    printf '不可读取：%s\n' "$f" >&2
    exit 2
  fi
done
```

这里是明确两文件白名单；`!`是否定。若用 `*`扩大范围，可能把不相关文件也读入，比赛里会出现错统计或泄露材料。字段、过滤状态和允许的未知值也应是明确规则，不让程序猜。

#### 4. 中间结果、幂等和完整输出

**幂等**在本周指重复运行同输入/规则不会叠加重复结果。`>> report.txt`每次追加会累积，不适合本题的最终统计；用新文件或明确覆盖派生结果，而不是覆盖输入。

可先写临时文件，核对成功才作为最终输出。所谓“原子替换”还要满足同一文件系统等条件，不能泛称所有移动都是原子的。本章脚本只向标准输出写最终统计，避免直接操作用户原件；由使用者选择工作区内的新结果路径。

若输出失败（磁盘满、无权限等），不能仅因解析过程成功就宣称报告保存完成。解析状态、文件写入状态与业务结论是三件事。

#### 5. 完整示例：统计状态并保留异常

下面脚本面向本周**七字段合成文本**，不是通用Web日志解析器。只接受一个本地可读普通文件；字段坏行、未知状态、注释和空行均计入摘要，输出合法状态统计。**异常被记录而不是“修好”；允许带异常的部分分析时退出0表示脚本按约定完成，不代表输入全有效。**

先读代码中新增awk语法：`变量++`加1，`数组[键]++`按键计数；`END { ... }`在全部输入处理后执行；`for (键 in 数组)`枚举键；`next`跳过本行后续规则；输出到 `/dev/stderr`是Bash/Linux类环境中的诊断通道路径。

```bash
#!/usr/bin/env bash
set -o pipefail
if [ "$#" -ne 1 ]; then
  printf '用法：bash count-status.sh 输入日志\n' >&2
  exit 2
fi
input=$1
if [ ! -f "$input" ] || [ ! -r "$input" ]; then
  printf '输入不是可读普通文件：%s\n' "$input" >&2
  exit 2
fi
awk '
  /^#/ {comments++; next}
  NF == 0 {blank++; next}
  NF != 7 {bad++; next}
  $4 !~ /^(200|302|401|403)$/ {unknown++; next}
  {counts[$4]++}
  END {
    for (code in counts) print code, counts[code]
    printf "lines=%d comments=%d blank=%d bad=%d unknown=%d\n", NR, comments, blank, bad, unknown > "/dev/stderr"
  }
' "$input" | LC_ALL=C sort
rc=$?
if [ "$rc" -ne 0 ]; then
  printf '处理管道失败：%s\n' "$rc" >&2
  exit "$rc"
fi
```

`!~`表示不匹配正则；`^(200|302|401|403)$`要求整个状态字段是四种之一。输入合法性先检查，随后把坏行分流。本脚本没有检测时间/IP格式，不得拿它当完整取证校验；它只完成状态计数契约。

如果没有Bash，用第三章逐行手算，仍可得到预期结果，但要记录“手算，脚本未在本人环境运行”。环境准备/排错超过约30分钟就转离线路线，避免花整周调安装。

## 六、Python：字节、文本、文件与异常

### 本章路线

从bit/byte和十六进制建立数据表示 → 区分字符与编码 → 学会 `bytes`/`str`转换 → 选择文件模式 → 确认路径 → 用具体异常和小函数保存错误。

> 本章要解决的问题：附件里的十六进制、中文日志和程序报错分别在哪一层？为什么看起来一个“字”并不总是一个字节？
>
> 本章学完应会：由给定字节推导数值/文本，运行并解释编码样例，区分二进制与文本读取，定位编码、路径和解析失败。

### 学习单元

#### 1. bit、byte与十六进制：先认识磁盘里的单位

**bit（位）**表示一个二进制位，只有0或1。**byte（字节）**在本周系统模型中由8个位组成。8个二进制位可有256种组合，一个字节按无符号整数解释时取值0—255；全0是0，全1是255。它还不是字符：**“字节的数值”与“按某编码解释后的字符”是不同动作**。

例如二进制 `01000001`，从右至左位权依次1、2、4、8、16、32、64、128；只有64和1对应的位为1，所以数值为65。十六进制每位取0—9、a—f，a为10，f为15，两位足够表示一个字节。`41`表示4×16+1=65，`ff`表示15×16+15=255。前缀 `0x41`只是提醒使用十六进制，不是字节多了两字符。

| 表示方式 | 同一个值 | 要避免的误会 |
| --- | --- | --- |
| 二进制 | 01000001 | 8位表示一个字节，不是8个字符的存储必然等价 |
| 十进制 | 65 | 这是数值，尚未选择字符编码 |
| 十六进制 | 41 | 两个十六进制数字表示一个字节 |

竞赛十六进制观察里 `41 42 43`是三个字节；如果文件实际存了文本 `"41 42 43"`，里面保存的是这些可见字符的编码，包含空格，不是同一字节串。第一个是数据，第二个是数据的文字表示。

#### 2. 字符、码点与编码：为什么“中”有三个UTF-8字节

**字符**是文本中的抽象符号；Unicode给字符等分配**码点**，例如A是 `U+0041`，“中”是 `U+4E2D`。码点是编号，不是磁盘存储方式。**编码**规定如何把文本编号变为字节序列，UTF-8是其中一种。

A在UTF-8中是一字节 `41`；“中”在UTF-8中是三字节 `e4 b8 ad`。因此文本 `A中`按Python字符串码点计数为2，UTF-8字节数为4。Python的 `len(str)`数码点，不保证等于屏幕上看到的字形数；组合字符/表情可能由多个码点构成，本周不要求掌握完整字形分段。

编码和解码方向相反：**encode**将文本变字节，**decode**按指定编码把字节解释成文本。同一字节可能不符合某编码，或按错误编码得到看似能显示的乱码。UTF-8不是所有文件默认编码；题目给定说明、BOM、工具结果可支持假设，但应保留验证依据。

这里给Python最小语法：`name = value`绑定变量；`print(...)`输出；引号内是字符串；`len(...)`求长度；`对象.方法(...)`执行该对象提供的动作。

```python
text = "A中"
raw = text.encode("utf-8")
print(len(text))
print(raw.hex(" "))
print(len(raw))
print(raw.decode("utf-8"))
```

对应输出：

```text
2
41 e4 b8 ad
4
A中
```

`.hex(" ")`把字节转成空格分隔的十六进制文字，便于观察，不是加密。需要按字节长度处理协议/二进制字段时不能直接用文本长度；HTTP正文长度如要按字节计，必须考虑实际编码后的字节，而不是屏幕字数。

#### 3. bytes与str：数据层和文本层分开

Python的 **str** 保存Unicode文本；**bytes** 保存0—255的整数序列。`b"AB"`是字节字面量，`"AB"`是文本，两者类型不同。bytes中的每一项可作为整数取出，`raw[0]`取第一项（索引从0开始）。

```python
raw = bytes.fromhex("41 42 e4 b8 ad")
print(raw[0])
print(list(raw))
print(raw.decode("utf-8"))
```

输出依次为 `65`、`[65, 66, 228, 184, 173]`、`AB中`。`bytes.fromhex`从十六进制**文字表示**恢复字节；`list`把序列展开为列表，用方括号表示一组有序值。这一步是表示转换，不是破解加密。

若运行 `raw.decode("ascii")`，会在中文字节处抛 `UnicodeDecodeError`，因为ASCII不支持这些字节。错误表明所选编码不能解释该输入，不说明文件“坏了”。用 `errors="ignore"`会删除不能解释的字节，可能把解题关键数据丢掉。正确做法是保留raw、记录编码假设和错误位置，再选择有依据的解码。

此外，不要用 `str(raw)`代替decode：它得到字节对象的表示（可能含 `b'...'`与转义），而不是按目标编码获得原文本。二进制附件未必应整体解码；应先识别结构，只对明确的文本区段解码。

<details><summary>解析</summary>

</details>

#### 4. 文件模式、编码和换行：读什么，返回什么

`open(path, "rb")`二进制读，返回bytes且保留原始换行字节；`open(path, "r", encoding="utf-8")`文本读，按编码返回str，默认通用换行处理可能把不同换行转成 `\n`。Windows常见CRLF字节为 `0d 0a`，Linux常见LF为 `0a`；显示行数相同不代表摘要相同。

```python
raw = b"A\r\nB\n"
print(raw.hex(" "))
print(raw.decode("utf-8").splitlines())
```

结果是 `41 0d 0a 42 0a`与 `['A', 'B']`。`.splitlines()`把文本按换行切成行，适合分析，但不会保存每个原始换行细节。完整性对照应对原bytes算摘要，而不是对“规范化文本”算完声称原件一样。

小文件可 `Path.read_bytes()`或 `read_text(encoding=...)`一次读入。大日志应用 `with open(...) as f:`和 `for ... in f:`逐行读；`with`保证离开代码块时关闭文件，缩进表示代码块范围。不要把运行样例生成的派生文件覆盖原件。

#### 5. pathlib与边界：可访问路径不是授权范围

`Path`让程序以路径对象处理文件：`/`用于拼路径，`.resolve()`解析绝对位置和符号链接，`.is_file()`判断普通文件，`.is_relative_to(root)`比较静态路径是否在根内。

```python
from pathlib import Path

root = Path("work").resolve()
source = (root / "input" / "access.log").resolve()
if not source.is_relative_to(root):
    raise ValueError("输入越出工作区")
print(source.name)
```

`from ... import ...`导入标准库对象，`if not`表示不满足时进入分支，`raise`主动报告错误；`source.name`取最后一段文件名，输出 `access.log`，不读文件内容。

这个演示只核对静态、可信本地练习路径；如果对方可以并发改符号链接，先检查后打开可能有竞态，并不是生产环境的完整隔离方案。无需在本周硬讲系统安全打开API，但必须说明边界。

#### 6. 异常与小函数：失败不能变成零结果

**异常**是程序用来报告错误的机制。函数用 `def`定义，把输入、处理、输出集中起来；`return`返回结果，不等同向屏幕打印。

```python
from pathlib import Path

def read_utf8(path):
    try:
        return Path(path).read_text(encoding="utf-8")
    except FileNotFoundError:
        raise ValueError("输入路径不存在")
    except UnicodeDecodeError:
        raise ValueError("UTF-8解码失败；保留原件并核对编码")
```

`try`尝试读取；两个 `except`分别接住文件不存在和解码错误，并抛可理解的错误；权限不足等其他异常仍应暴露，不能无条件吞掉。这个函数不会返回“0事件”，因为它只负责文件读取；业务分类应等下一层解析成功后进行。

测试时不用一次写整个程序。先用小字节例子验证decode，再用已知一行文本验证读取，最后引入坏编码、缺文件等边界。这使你知道错误发生在路径、文本还是业务字段层，而不必猜大脚本哪里坏了。

### 本章路线

先认识JSON实际结构和Python类型 → 理解JSONL一行一值 → 分开语法解析、字段校验和业务分类 → 连接会话事件与访问 → 交付能复算的小报告。

> 本章要解决的问题：结构化数据里哪种是损坏、哪种是缺字段、哪种是未知业务值？怎样关联而不吞错或过度归因？
>
> 本章学完应会：逐行读JSONL，给出有效记录和错误明细；按显式规则关联，并说明结果支持范围和剩余证据缺口。

### 学习单元

#### 1. JSON对象、数组和值：不要只认识一个名字

**JSON**是交换结构化数据的文本格式。对象写 `{...}`，由键/值对组成；数组写 `[...]`，是一组按顺序排列的值；字符串使用双引号；还可有数字、true/false和null。**对象不是只有JSON字样的普通句子，字段有明确结构和类型。**

```json
{"user":"alice","attempts":2,"ok":true,"session":null,"roles":["student"]}
```

这里user是字符串、attempts是数字、ok是布尔值、session是空值、roles是字符串数组。不能将 `"2"`与 `2`混为一谈，也不能把字符串 `"false"`当布尔false。JSON要求双引号和规定语法，Python字典的单引号显示不自动成为合法JSON。

Python的 `json.loads`接收JSON文本并返回Python值；`json.dumps`反过来序列化为JSON文本。常见对应关系如下：

| JSON值 | Python值 | 使用时注意 |
| --- | --- | --- |
| object / array | dict / list | dict按键访问，list按索引访问 |
| string / number | str / int或float | 字符串数字不自动转整数 |
| true / false / null | True / False / None | 拼写不同，null不等于字段缺失 |

```python
import json
record = json.loads('{"user":"alice","result":"success"}')
print(record["user"])
print(json.dumps(record, ensure_ascii=False))
```

第一行输出alice。`record["user"]`按字典键取值，键不存在会报错；`ensure_ascii=False`让非ASCII字符直接输出，不改变原含义。序列化显示顺序/空格可能改变，不能对dump后的文本算摘要就声称原始字节未变。

#### 2. JSON与JSONL：整个值和逐行值不同

一个JSON文件可包含一个对象，也可包含一个大数组。**JSONL**的惯例是一行一个完整JSON值；本周进一步规定每个非空行必须是事件对象。两个对象连在不同物理行，并不是一个普通JSON文档；一次 `json.loads`整份JSONL可能因多个顶层值报错。

```text
{"event_id":"a","result":"success"}
{"event_id":"b","result":"denied"}
```

这里有两个事件，需逐行loads。反例：对象跨两行排版虽可能是合法JSON，却不符合一行一事件的本题JSONL契约。文件含空行也应记录为格式异常/空白，不能声称每行都有效。

Python可用 `for number, line in enumerate(f, 1):`逐行遍历。`enumerate`给每项加编号，1是起始行号；`line.strip()`只可用于判断是否空行，不应不加说明地改写原文，保留原行便于回指。

#### 3. 三层处理：语法、结构与业务，不是一种失败

先用loads判断语法；成功后检查是否对象、必要字段和类型；再按action解释result。三层例子：

```text
{"user":"a","result":"success"       ← 少右括号，语法错误
{"user":"a"}                          ← 语法合法，但必要字段缺失
{"user":"a","result":null}           ← 字段在，但值类型不符合本题
{"user":"a","result":"maybe"}        ← 类型正确，业务值未知
```

判断“缺失”用 `"result" not in row`，别用 `row.get("result") is None`同时吞掉缺失和null。业务未知不等于denied：将maybe强映射为失败会污染题目答案，强映射为成功同样错误。

完整处理器如下，接收**一段文本**而不是直接改文件，便于先用小样例测试。新增语法：`[]`建立列表，`append`追加；字典保存计数；`isinstance`查类型；`continue`进入下一行。`rules`按动作保存允许结果，本周login允许success/denied，authorize允许allow/denied，logout允许success；这些是明确教学规则。

```python
import json

def analyze_jsonl(text):
    stats = {"lines": 0, "blank": 0, "parsed": 0,
             "parse_errors": 0, "schema_errors": 0,
             "known": 0, "unknown": 0}
    rows, errors = [], []
    required = ("event_id", "time", "action", "user", "source", "session_id", "result")
    rules = {"login": {"success", "denied"},
             "authorize": {"allow", "denied"},
             "logout": {"success"}}
    for number, line in enumerate(text.splitlines(), 1):
        stats["lines"] += 1
        if not line.strip():
            stats["blank"] += 1
            errors.append({"line": number, "kind": "blank"})
            continue
        try:
            row = json.loads(line)
        except json.JSONDecodeError as exc:
            stats["parse_errors"] += 1
            errors.append({"line": number, "kind": "parse", "reason": exc.msg})
            continue
        stats["parsed"] += 1
        if not isinstance(row, dict):
            stats["schema_errors"] += 1
            errors.append({"line": number, "kind": "schema", "reason": "不是对象"})
            continue
        missing = [key for key in required if key not in row]
        bad_types = []
        if not missing:
            bad_types = [key for key in required if key != "session_id"
                         and not isinstance(row[key], str)]
            if row["session_id"] is not None and not isinstance(row["session_id"], str):
                bad_types.append("session_id")
            if row["action"] == "authorize" and not isinstance(row.get("object"), str):
                bad_types.append("object")
        if missing or bad_types:
            stats["schema_errors"] += 1
            errors.append({"line": number, "kind": "schema",
                           "missing": missing, "bad_types": bad_types})
            continue
        known = row["result"] in rules.get(row["action"], set())
        stats["known" if known else "unknown"] += 1
        rows.append({"line": number, "data": row, "known": known})
    return stats, rows, errors
```

列表推导式 `[key for key in required if ...]`是遍历并收集满足条件的键；`set()`为空集合，未知action不匹配任何已知结果。字典三目键 `"known" if known else "unknown"`按条件选计数项。代码保留行号，错误与正常结果分开；没有校验时间内容、IP格式、重复ID或会话有效性，那属于下一层规则，不能称“完成全量安全校验”。

##### 小练习：null和没有键有什么不同

> 题源：依据Python json类型映射自拟错误审查。

三个对象分别为 `{"result":null}`、`{}`、`{"result":"maybe"}`；本題要求result必须字符串且业务只能success/denied。给各自错误层，并解释为何 `if not row.get("result")`不够。

<details><summary>解析</summary>

null是存在但类型错误，{}是缺键，两者结构错误原因不同；maybe为结构合法、业务未知。get/真假判断会把null、缺键、空串等混在一起，又会把非空maybe当“有结果”，不能形成准确分类。应按键存在→类型→业务值顺序判断。

</details>

#### 4. 关联管线：每一步要可追溯

文本解析器不负责“谁攻击了谁”。需要先把合法事件按给定会话ID组织，再把访问按相同ID候选关联，并保留对象/时间。`session_id=null`不允许作为“共同的空会话”关联所有未知用户。

例子：e1是login success、s1；r1是GET /admin、s1、403；e2是login denied、session=null；r2是缺会话访问、同来源、200。可建立e1↔r1同会话候选；不能用null把e2↔r2连成登录成功，也不能用同IP替代缺失身份。

若认证事件有多个同ID、时间不一致或原字段缺失，报告候选和矛盾。关联结果支持会话级活动整理；仍需唯一ID保证、完整性、时间基准和授权规则才能下更强结论。第4章的事实分层在这里继续使用。

#### 5. 报告、题目输出与团队交接

**题目输出**是题目要的值或解释；**交接报告**是让别人复核值的证据。不因写了长报告就忽视输出格式，也不因题目只收一个数字就丢掉内部步骤。

最小报告包括输入摘要、处理规则、计数、异常行、关键关联、结论和未决事项。示例“parsed=6”还需说明它包括缺字段的记录；若题目问可用于业务关联的行，不能把parsed直接当有效数。即使都叫“成功解析”，统计口径也可能不同。

交接时给队友具体复核动作，例如“查看原第6行缺result，再运行校验确认schema_errors=1”。隔日换一行后，应预测变化再重跑；这种回归比“能解释JSONL意义”更接近赛题能力。

> 题源：第二周原JSONL合成输入；赛题式结构化日志取证，不是真实服务观测。

### 本章小结

JSON先教结构和类型，JSONL再教行契约。解析、字段校验、业务判断、关联和报告是不同层；每层有自己的输入、输出和失败判据。缺失值、null、未知值都不该被“凑一个成功率”吞掉。

本题缩小契约：每非空行必须对象且含字符串action/result；login允许success/denied。完整4行如下：

任务：逐行给类别，算parsed、schema error、parse error、known、unknown；指出若对整份文本一次loads会怎样。

#### 练手2：弱关联与变式的精确变化（任务14）

> 题源：自拟认证/访问关联和回归题。

给定login事件 `user=u, source=ip-a, session_id=s7, result=success`；访问记录为 `user=u, source=ip-a, session=s7, object=/admin, status=403`。随后在事件副本删除session_id，其余不变。任务：原关联支持什么？删字段后完整契约如何分类，强关联还能否自动继续？是否可退化为“同IP就同人”？

<details><summary>解析</summary>

原来支持给定同会话的登录与后台拒绝活动，不证明授权成功或实际人身份。删键后结构错误加1，该事件不能按完整契约进入强关联；保留原文和错误，若另做用户/时间候选必须写新规则、降低证据等级。不能静默用IP替代ID，也不能把移除ID说成权限修复。

## 八、练习提示与常见问题

**不知道怎样起步时，先写三句话：**题目要的输出是什么？我真正拥有的输入是什么？哪个字段/字节区段能回答它？随后才选择命令或脚本。把“我要算后台403的来源次数”与“grep一下403”区分开。

- 结果为空：先看实际输入位置、错误、退出状态和重定向去向，不立即推成安全或零事件。
- 结果不一致：核对摘要、字段契约、筛选范围、版本/语言环境和时间基准；不要为了和队友一致而改原数据。
- 代码不懂：回到相应章的首次语法讲解，不以“命令能运行”替代理解。`$4`、NF、decode、loads各有不同输入层。
- 证据不足：写具体缺失字段/来源，保持能由已知条件支持的结论；不一律说“无法判断”也不编身份/因果。
- 提示使用：先提示材料/字段，再提示方法顺序，最后给局部命令；记录提示等级，隔日用新输入复测。

## 十一、自测参考答案

1. 工作目录是相对路径的起点，不是自动等于脚本目录。从out起算会找错位置，应明确基准或传 `../input/...`，同时记录解释器、输入摘要和状态。
2. 固定串会命中路径或坏行，字段规则才判断状态；uniq只合并相邻重复，先sort使同值相邻再计数。
3. “中”UTF-8为 `e4 b8 ad`三字节，str一个码点；文本encode得bytes，bytes按已知编码decode得str。错误编码应暴露，ignore会丢数据。
4. 三层不等价：坏JSON是语法错；合法JSON也可能数组/缺键/类型错；结构合格还可能业务未知。统计必须声明口径和错误行。
5. 给定唯一会话ID可支持会话活动关联，不自动证明真实人或权限；同IP通常仅是来源线索，缺用户/会话不能归同一主体。
